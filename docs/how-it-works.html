🔬 Deep Dive — Architecture Details

📝
Planner System Prompt
What the LLM sees on every call
  • cached Static preamble + tool catalogue (28 tools, ~3k tokens). Prompt-cached across calls.
  • dynamic Dataset profile: column names, types, row count, sample row — per-question.
  • RAG Top-5 retrieved few-shot examples from IndexedDB, embedded at call time.
  • fence Dataset values wrapped in <<<UNTRUSTED>>> fence — prompt injection guard.
  • retry If validatePlan() fails, error message appended and model asked once more.
📦
Plan JSON Structure
What the LLM must return
  • goalHuman-readable sentence describing what the plan will do.
  • dataset_refsArray of dataset names the plan will read. Validated against loaded datasets.
  • assumptionsOptional clarifying notes the model makes about the question.
  • steps[]Ordered tool calls. Each step: id, tool, args, output_var, why.
  • last stepMUST be render.* or report.* — enforced by validatePlan().
🛠
28 Registered Tools
Available in every plan
  • stats.*aggregate, summary_stats, hex_bin, density_grid, morans_i, getis_ord_gi, distance_matrix
  • geometry.*buffer, intersect, union, difference, dissolve, centroid, convex_hull, voronoi, simplify, reproject
  • joins.*spatial_join, nearest_neighbor, point_in_polygon
  • sqlRaw DuckDB SQL. Sanitised with allowlist parser before execution.
  • render.*map, chart, table, summary
  • report.*quickscan — auto describes a dataset
  • geocodeAddress → lat/lon via Nominatim

Full annotated execution sequence
1. pushData(file)
CSV/GeoJSON parsed by DuckDB-WASM. Schema introspected. DatasetProfile built (columns, sample row, row count). Emits dataset-loaded event.
→
2. RAG embed (optional)
Question embedded in-browser. kNN search over IndexedDB corpus. Top-5 examples appended to system prompt. Disabled in agentic mode (inspection probes replace static examples).
→
3. callForcedTool()
POST /v1/chat/completions with tool_choice="submit_plan". Provider: gpt-oss-120b. Returns tool_calls[0].function.arguments → raw Plan object.
↓
4. validatePlan()
canonicalizeStepIds() → zod PlanSchema parse → tool existence check → args parse → output_var forward-ref check → last step = render.*. If fail, retry with error feedback once.
→
5. plan event → approvePlan()
Widget dispatches plan event. Host (or headless auto-approve) calls approvePlan(planId). _pendingPlan cleared. _execute() fires as fire-and-forget.
→
6. Executor step loop
Each step runs its runner (runners/render.ts, stats.ts, etc.). SQL steps pre-validated. Output stored in Map<output_var, ArrowTable>. Progress events fire per step.
↓
7. Critic (on failure)
Step error? Critic LLM sees: original plan + failing step + error message. Returns patched step. Executor retries the patched step once. AbortSignal propagated.
→
8. Result payload
render.*/report.* runner returns: {kind: "summary"|"table"|"chart"|"layer", …data}. Emits result event. result-canvas mounts the matching renderer component.
→
9. Persist + display
Layer added to map Contents. Result saved to IndexedDB Saves store. Approved (question, plan) pair optionally saved as future few-shot via memoryEnabled flag.
