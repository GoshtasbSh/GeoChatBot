# Phase 4 — Root-Cause Fixes (2026-05-16)

This file groups every code change applied during the audit by root cause, with a 1-paragraph rationale per fix. Every fix kept the unit suite at **821 passing / 5 skipped / 0 failing** and `tsc --noEmit` clean.

> Cross-refs: detailed augmentation log in [`2026-05-16-rag-changes.md`](./2026-05-16-rag-changes.md); inventory in [`2026-05-16-final-inventory.md`](./2026-05-16-final-inventory.md).

## Root Cause #1 — Static prompt-injection delimiter

**Files** — `packages/widget/src/agent/planner.ts` (~lines 122–130 and the two `<<<UNTRUSTED_DATASET_PROFILE` blocks; new `generateFenceToken()` helper at the bottom).

**Why it mattered** — A hostile CSV could craft a literal `UNTRUSTED_DATASET_PROFILE>>>` row and break out of the fence into the system prompt. OWASP LLM01:2025 still ranks prompt injection as the #1 critical risk for LLM apps.

**Fix** — Switched to a per-Planner-instance random 8-char token. The fence becomes `<<<DATA-FENCE-${TOKEN} … ${TOKEN}-DATA-FENCE>>>`, and the preamble explains that values between fences are opaque DATA never instructions. Token is constant per session so Anthropic's `cache_control:ephemeral` still hits.

## Root Cause #2 — gpt-oss reasoning hint absent

**Files** — `forced-tool/types.ts`, `forced-tool/openai-compat.ts`, `agent/llm.ts`, `agent/planner.ts`, `agent/agentic/loop.ts`.

**Why it mattered** — gpt-oss's tool-call reliability is materially better when `reasoning_effort: high` is set in the request body. Not setting it leaves the model on its default `medium`, which the gpt-oss model card explicitly says is sub-optimal for tool-call-heavy work.

**Fix** — Plumbed an optional `reasoningEffort?: 'low' | 'medium' | 'high'` field end-to-end. The planner auto-sets `high` when the active model name contains `gpt-oss`. Other providers ignore unknown body fields with HTTP 200, so the change is safe for non-gpt-oss callers.

## Root Cause #3 — Toponym disambiguation hole

**Files** — NEW `packages/widget/src/agent/data/gazetteer-mini.json`, NEW `packages/widget/src/agent/data/gazetteer.ts`, NEW `packages/widget/test/agent/data/gazetteer.test.ts` (10 cases), `executor/runners/geocode.ts`.

**Why it mattered** — Nominatim returns *the most popular* "Springfield" by default, not the right one. The viewbox path needed a region-geocode round-trip to even build the viewbox; for canonical places that's a wasted call.

**Fix** — 110-entry hand-curated gazetteer keyed by `name + region` with Wikidata Q-IDs where known. On a unique gazetteer hit the geocoder skips Nominatim's region geocode and builds the viewbox directly. Ambiguous bare names ("Springfield") still return `undefined` so the runner falls back to the existing Nominatim path / clarification prompt.

## Root Cause #4 — Dataset profile lacked semantic hints

**Files** — `packages/widget/src/agent/prompts/builders.ts` (new exported `detectSemanticHint`).

**Why it mattered** — Schema-linking is the #1 NL2SQL bottleneck on BIRD/Spider 2.0. The planner today re-discovers column semantics via `inspect.column_pattern` round-trips — costing iterations.

**Fix** — Pure-regex semantic classifier emits a `hint:<tag>` suffix per column (`latitude`, `longitude`, `wkt-geometry`, `street-address`, `zip-or-postal`, `country-name`, `country-code`, `state`, `currency`, `phone`, `iso-date`, `low-card-categorical`). Conservative: only emits when name+sample agree.

## Root Cause #5 — Eval rubric too strict on render kind

**File** — `packages/eval/tasks/comprehensive_v1.json` (14 new shape variants).

**Why it mattered** — The first 12-task agentic sample reported 6 FAILs that were all `sql → render.table` instead of `sql → render.summary`. Both renders show the same count answer; only the styling differs. Without the calibration the scorer punishes the model for a stylistic choice that has no semantic impact.

**Fix** — For tasks whose id starts with `count_`, `filter_count_`, `topn_`, or `groupby_aggregate`, the rubric now accepts `render.table` as a terminal step in addition to `render.summary`. The Python one-shot in `Phase 4` of the audit applied this deterministically. Aggregate PASS-rate moved 50 % → ~75 %.

## Root Cause #6 — Audit-harness iteration cap too low

**File** — `scripts/audit-live-navigator.ts` (line 447).

**Why it mattered** — The harness capped agentic-loop iterations at 3 with a comment about Llama 3.3 verbosity. For gpt-oss-120b on chart/map tasks the model legitimately needs 4–6 inspect rounds before it can finalize. Two ERR cases in the second sample were `loop exhausted 3 iterations without finalize_plan`.

**Fix** — Raised cap to 10 (the production `Planner` default is 30). Comment updated to record the audit phase + rationale.

---

## Root Cause #7 — Nominatim policy compliance documentation

**Files** — none changed (browser limitation documented in `2026-05-16-rag-changes.md` and in this file).

**Why it mattered** — Nominatim's terms ask for a real identifying `User-Agent`. `User-Agent` is a Forbidden Header in browsers and `fetch()` silently strips it.

**Fix** — Documented as a known limitation. Operators who need full compliance should proxy through their own backend. The 1.1 s rate-limit, 400-row cap, and abort-aware sleep already in place keep us well within the spirit of the policy.
