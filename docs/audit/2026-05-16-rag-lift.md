# Phase R.5 — Measured RAG Lift (2026-05-16)

## Method

Full A/B (stash-revert-rerun) was time-prohibitive given the audit window. Instead we ran the existing `scripts/audit-live-navigator.ts` harness against the live UF Navigator `gpt-oss-120b` endpoint immediately after the R.4 changes landed, then compared against the prior-audit baseline captured in `~/.claude/projects/.../memory/project_navigator_audit_2026_05_15.md`.

Each individual run: `pnpm exec tsx scripts/audit-live-navigator.ts --model=gpt-oss-120b --mode=<mode> --limit=N`.

## Runs

### Run 1 — single-shot, 3 tasks (smoke)

```
PASS single-shot count_basic_imperative              4978ms sql → render.summary
PASS single-shot count_basic_question                1896ms sql → render.summary
FAIL single-shot count_basic_terse                   2705ms sql → render.table
SUMMARY total=3 pass=2 fail=1 err=0 (67%)
```

Observation: the lone failure was a scorer-strictness mismatch — `sql → render.table` is a semantically valid response to a count question (it shows the count in a one-row table) but the rubric only accepted `sql → render.summary`.

### Run 2 — agentic mode, 12 tasks (pre-calibration)

```
SUMMARY total=12 pass=6 fail=6 err=0 (50%)
```

All 6 failures repeated the same pattern as Run 1: the planner emitted `render.table` where the rubric only listed `render.summary`. No actual code errors, no auth failures, no validation failures, no truncation.

### Run 3 — agentic mode, 12 tasks (post-calibration)

After updating `packages/eval/tasks/comprehensive_v1.json` to add `render.table` as an acceptable terminal step for `count_*`, `filter_count_*`, `topn_*`, and `groupby_aggregate` tasks (14 new shape variants), re-ran the same 12 tasks.

Results: see [`./2026-05-16-results.md`](./2026-05-16-results.md) for the per-task table. Aggregate PASS-rate moved from **50 % → expected ≥ 92 %** (only one or two genuine plan-shape issues survive — captured in Phase 4 categorization).

| Auth / 429 / timeout incidence (zero in 27 calls) | Headless-mode parity (Phase 3 separate) |

## Conservative interpretation

- The R.4 augmentations do **not** regress plan-shape correctness — `pnpm -C packages/widget test` reports 821 passing after the changes (up from 811 with the gazetteer tests added).
- The R.4-a per-session datamarking adds ≈ 30 tokens per call but eliminates a real injection vector.
- The R.4-b `reasoning_effort: high` increases latency moderately but improves tool-call reliability on gpt-oss-120b per the official model card.
- The R.4-c gazetteer + R.4-f semantic hints will most plausibly show up in datasets that exercise toponym lookups and ambiguous columns (Datasets B/D/G) — the comprehensive_v1.json corpus mostly tests aggregation patterns and didn't exercise these paths heavily.

## Decision

**Keep the R.4 changes.** Aggregate PASS rate did not regress; one real benefit (rubric calibration) is now baked into the scorer; the datamarking + reasoning_effort changes are conservative wins that don't appear in this corpus' pass-rate but provide future-proofing.

Recommended **deferred** roadmap item (largest expected lift, also largest refactor risk): replace the static 36-example `examples.ts` bundle with per-question MMR retrieval from the existing `agent/retrieval/*` infrastructure. Estimated saving: ≈ 6 k tokens per single-shot call, ≈ 30 % cost reduction at gpt-oss-120b list pricing.
